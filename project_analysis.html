End-to-End Pipeline

An Amazon order triggers data into SQL Server. Every 3 seconds run_loop.py polls for unprocessed rows, routes them through batch_processor.py, and either writes a pure-Python CMYK PSD or hands the job to the Photoshop UXP plugin via a JSON job-queue. Finished PSDs are uploaded to the Synology NAS.

Path A — Pure Python PSD Writer

Used when Photoshop is not running or USE_PHOTOSHOP_BRIDGE=0. batch_processor.write_psd() builds a valid CMYK PSD entirely in Python using struct + zlib. No Photoshop dependency. Slower rendering for SVG/premium fonts (Chrome subprocess per glyph).

Path B — Photoshop UXP Plugin

Preferred path when USE_PHOTOSHOP_BRIDGE=1 and Photoshop.exe is running. ps_bridge.py writes a job JSON → UXP plugin (index.html) polls every 3s, opens the template, places layers, exports PSD. Better for template fidelity.

Architecture Notes

Two Rendering Paths (intentional)

The Python PSD writer is the independence-guaranteeing fallback — it runs with zero Photoshop dependency on any machine. The UXP path is higher fidelity (real layers, live text, template-accurate placement) but requires Photoshop to be open. USE_PHOTOSHOP_BRIDGE in .env controls the default; batch_processor also auto-detects whether Photoshop.exe is running.

Font Rendering Stack

Standard fonts: PIL renders directly (fast). Premium SVG fonts (camo, glitter, paint): Chrome headless renders glyph-by-glyph via @font-face CSS, captures PNG, composites. Three strategies attempted in sequence with fallback. Slowest path is ~20s per glyph on cold Chrome.

Job Queue — File-Based

The bridge between Python and the UXP plugin is a folder of JSON files — not a proper message queue. This is pragmatic (no extra infra) but means: no acknowledgement, no retry-on-crash, no ordering guarantee. The done/error folders accumulate indefinitely. Acceptable for current volume; would need revisiting at 500+ orders/day.

NAS Dependency

Output PSDs go to local C:\Varsany\Output\ first, then uploaded to Synology NAS. If NAS is unreachable, local files persist but the India↔UK sync stalls. upload_nas=False flag in export scripts is the current workaround. Long-term: a retry queue for failed NAS uploads.

Quantity & Multi-Zone Handling

Quantity >1 stacks copies vertically on one canvas (1cm gap) — printing team cuts apart. Multi-zone (front+back+sleeve) stacks zones vertically in combined mode. The UXP plugin handles both via canvas expansion + copyMerge paste. The Python path handles quantity but stacks zones into separate files.

Semi-Custom (Football Jerseys)

A distinct code path: no image placement, only text substitution into named Photoshop template layers (e.g. "Player", "08"). Multi-item stacking in v3.7 was reworked to open a fresh template copy per item then paste into the main document — fixes the v3.6 document-confusion bug.

Top Recommendations

1. Move hardcoded secrets to .env (immediate)

NAS password in synology_upload.py is committed to git history. Rotate the NAS password, update .env.example, and read from os.environ. Run git filter-branch or BFG Repo Cleaner to scrub history if repo is shared.

2. Parameterise SQL queries (immediate)

Any string interpolation into SQL is a potential injection. Replace with cursor.execute(sql, params) throughout batch_processor.py and db.py.

3. Add process lock to run_loop.py

A single daemon.pid file prevents double-processing. On Windows: msvcrt.locking() or simply write PID and check on startup.

4. Atomic job file writes (ps_bridge)

UXP should write to {id}.tmp then os.rename() to {id}.json. Python should only pick up .json extension files. This eliminates the partial-read race condition.

5. Pin requirements.txt

Run pip freeze > requirements.txt on the working machine and commit the result. Prevents silent breakage on next fresh install.

6. CLI-ify the one-shot scripts

export_today.py, get_order.py, count_orders.py all need manual code edits to change dates/order IDs. Add argparse to make them reusable without touching source.
